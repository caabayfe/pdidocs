View changeset (Application)

A changeset is a draft copy of an application that you can update and save as often as needed. When you are satisfied with your changes, you can commit the changeset, which applies those changes to the application.

You can update config data in an existing changeset, or in a new changeset. You can save your changes for later updates, or save and commit the changes. Committing the changes generates a snapshot for each deployable that is affected by the changes.

  • When you commit the changes that you have made to an application (commit the changeset), the system generates a snapshot of each deployable that has been updated. A snapshot is an exact record of the config data for a deployable.

    Snapshots are read-only — you cannot modify a snapshot. You can, however, start a new changeset that is based on a particular snapshot.

  • If another user has committed changes to a data set (thus creating a new snapshot) while you are working on a changeset of the same data, then the data that you are working on is stale (the data is in the state it was in before the other user committed changes). This can result in data conflicts.

Details

Changeset details that tie the changeset to the application.

Config data

Tree containing all of the config data for the changeset. You can click an entry in the tree to view specific configuration details.

Activity

List of all changesets, committed and open, for the component library.

Changeset actions

  • Create a changeset to edit the config data. The changeset includes the full config dataset of the application.
  • Save a changeset to update it. You must commit a changeset to update the config data for the application (changes appear on the Activity tab).
  • Edit an existing changeset that has been saved, but not committed.
  • Commit a saved changeset. The system updates the application to persist the changes to config data, and the changeset state changes to Committed.

    A changeset cannot be modified. If an error occurs during the commit process, the changeset state is set to Commit failed. The system generates a snapshot of each deployable that is affected by the changes.

    An open changeset with conflicts is blocked—it cannot be committed. A warning message appears, and the State in the header changes from Open to Blocked.
