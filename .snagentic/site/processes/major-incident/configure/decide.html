    Promoting and rejecting - configuration

    Technical referenceReviewed 2026-10-17Checked against pdi2 on 2026-10-20 (mirror d13485ddb833)Operator guide: Promote or reject a candidate

    Promote, or create

    The creation mode is promote E03: Promote to Major Incident E01 accepts the candidate itself; Create Major Incident E04 (new parent, candidate as child) never shows. Both need major_incident_manager through canApproveMIC() E02.

    Assignment on promotion CORRECTED

    The group comes from the property sn_major_inc_mgmt.major_incident_management_group, which only sn_mim_admin can read or write. E07 E08 Its value is private to that role, so the record doesn't show it, but on screen it is empty E10: the group never changes on proposal or promotion, and the reassignment emails are never queued. E11 Promotion still makes the promoter the assignee when they belong to the incident's current group. E07 Set the property to the major incident team's sys_id if promotion should hand the incident over.

    Rejection has no server-side role check OPEN QUESTION

    Security observation: only the UI conditions require a major incident manager. The form action checks canRejectMIC() E02 E05, and so does the list action's visibility E15, but the client-callable function it calls, MIMListActionsUtil.rejectMIC, checks only itil or sn_incident_write E06. The workbench REST operation is open to anyone with workbench access E09, and its REJECT branch sets the state with no role or state check, while its PROMOTE branch does check the role. E16 So any service desk user who calls these endpoints directly can reject a candidate. Platform team: add a major_incident_manager check on the server, or accept the risk explicitly.
