    1. Dependency views NEW

    The three field actions are on task, so a change gets them with no change-specific record: CI dependency view (cmdb_ci), Service dependency view (business_service) and Service offering dependency view (service_offering), each shown when its field has a value, with no required role. E01 E02 E03 Each opens the unifiedmap route rooted at the field's value, five levels deep. E04 E05 What the map shows is governed by CMDB read access. Whether change requesters may edit CMDB connections from the map, or only CMDB roles, is not decided yet. shared/Q05 The same records are described for incidents in Dependency views and impact lists.

    2. The related lists NEW

    Both change layouts put task_ci first, then task_cmdb_ci_service and task_service_offering, and task_outage last. E06 E07

    Kept in step by business rules, in this order:

    change.conflict.mode is private and redacted in the mirror. E11 Q18 In advanced mode conflict detection checks every affected CI, so Affected CIs matters for scheduling as well as impact.

    6. CI subscribers NEW

    Affected ci notifications queues an event for any task, changes included, when its state changes E45, but the only CI affected notification is on incident. E46 Subscribers aren't told about changes; adding a change notification would be a process owner's decision.
