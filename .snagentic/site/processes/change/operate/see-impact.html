    8. See what a change affects

    For: Change requester, Technical approver, CAB member or managerWhere: Service Operations Workspace, the classic incident formChecked against pdi2 on 2026-10-20 (mirror fcd5bcad66af)

    When to use it NEW

    A change names a Configuration item, often a Service and a Service offering. Before you ask for approval, and when you approve, look at what else depends on them: the risk, the window and the approvers all follow from it.

    You areUse it to
    the change requesterkeep Affected CIs complete while the change is in New, so the impacted services and the conflict check are right
    a technical approvercheck that the affected and impacted lists match the plans before you approve (see Approve as a technical approver)
    a CAB membersee which services the change hits, and how far, before the board decides (see The change advisory board)

    The lists are on the change's Related records: Affected CIs, Impacted Services/CIs and Outages. E01 E02 The same views on an incident are in See what the incident's configuration item affects; the CMDB side is in See what depends on a configuration item.

    Open the dependency view NEW

    Transcript (6 steps)
    1. Start. Start by filling the configuration item on the change, or its service or service offering.
    2. Look. Choose the tree icon beside the field. A map tab opens, centred on the item, with five levels of connections around it.
    3. Affected. The change's own item is kept in affected CIs for you. Add every other item the plans touch, while the change is still new. After that, the list is locked.
    4. Impacted. When the change leaves new, the impacted services are rebuilt in the background from every affected item. Services you added by hand stay.
    5. Outage. If the work takes a service down, record it with create outage on the outages list.
    6. Decide. Technical approvers and the change advisory board read these lists, with the plans, before they decide.

    Download the video (MP4)

    1. Open the change in the Service Operations Workspace and fill Configuration item (or Service, or Service offering).
    2. Choose the tree icon beside the field: CI dependency view, Service dependency view or Service offering dependency view. It appears only when the field has a value, and needs no special role. E03 E04 E05
    3. A Map tab opens, centred on that item, with five levels of connections around it. E06 Q28
    4. Use Apply filters to narrow the CIs, Open in new map to centre on another CI, and Related items or Attributes to read a selected one. E07

    The map can also create and delete connections, and warns that deleting one "might result in an invalid CMDB state". E07 Don't change the CMDB from a change's map: what the change will alter is planned in the change itself. Q08

    Keep Affected CIs complete NEW

    • The change's own Configuration item is added to Affected CIs for you, and replaced when you change the field. E08
    • Its Service is added to Impacted Services/CIs in the same way. E09

    To add more, choose Add on Affected CIs and pick configuration items; filter by Configuration Class to find them faster. E10 E12 On the classic form, Add opens the Add Affected CIs dialog. E16 Remove takes rows away, except the change's own CI: change the field on the form instead. E15

    Do it while the change is in New. After that, Add is hidden, and a change that follows a change model refuses to add or remove: "Affected CIs cannot be modified for Change Requests in this state". E10 E11 E13 E14 A model can allow it in later states; ask the change manager if you need to. E11 Q19 Add and Remove also appear only if the platform team lists changes in com.snc.task.associate_ci. E10 Q17

    Impacted services are worked out for you NEW

    When the change leaves New (when you request approval, for a normal change), the impacted services are rebuilt in the background from every affected CI, not only the change's own CI. E17 E18 The refresh:

    • removes the services it added before, and keeps those you added by hand or that came from the Service field E19 E20;
    • adds the services the affected CIs belong to, and the services of CIs with scheduling conflicts E19 Q20;
    • tells you when it is done: "Refresh impacted services for change request CHG… has completed". E19 Q29

    So an affected CI added after New doesn't reach the impacted services. On the classic form, Refresh Impacted Services in the form menu runs the refresh again, where the platform team has switched it on. E21 Q17

    Record an outage NEW

    If the work takes a service down, record it on Outages: in the workspace, Create outage opens a new outage, and Add links one that exists. E23 E24 The workspace's More actions menu doesn't offer it. E25 On the classic form, Create Outage in the form menu fills in the change's CI, number and short description (for itil and sn_change_write). E22

    Who is told NEW

    Nobody, from these lists: people subscribed to a CI are emailed only about incidents, not about changes. E26 If the service's users need to know, tell them yourself.

    Tips

    • Set the CI before you open the view: the button isn't there while the field is empty. E03
    • Add every CI the plans touch before you request approval: the impacted services, and so the approvers' and CAB's view, are built from them. E17 E18
    • As an approver, if a CI from the implementation plan is missing from Affected CIs, reject with that question: the change has to go back to New to fix it. E11
