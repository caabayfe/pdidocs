    Escalation and trigger rules - configuration

    Technical referenceReviewed 2026-10-19Checked against pdi2 on 2026-10-20 (mirror 9f3658cfb43d)Operator guide: Set the escalation and trigger rules

    The records NEW

    Two parts of the On-Call Scheduling plugin decide what happens when urgent work arrives:

    PartTables
    Escalation policythe shift (cmn_rota: catch-all, custom escalation, override user preference), its rosters, escalation sets (cmn_rota_escalation_set), steps (cmn_rota_esc_step_def), group escalations (on_call_group_escalation), shift contact preferences (cmn_rota_contact_preference), channel configs (on_call_communication_channel_config)
    Trigger rulestrigger_rule, which extends sysrule_assignment E03, and trigger_rule_table_cfg

    On pdi2 there are no trigger rules E01 Q02 and no escalation has run. E02

    1. Trigger rules: who can write them NEW

    The Trigger Rules module is for rota_admin and rota_manager. E04 Creating needs rota_admin or managing any group E05; reading and writing a rule needs managing its group. E06 E07 Only rota_admin gets the Script action. E07

    2. Trigger rules: saving one NEW

    In order of execution:

    1. Set trigger rule table cfg links the table's configuration (group, user and journal fields). E08
    2. Clear group field for Global Rules: a rule on changes to the group field applies to all groups. E09
    3. One default group assign rule per table: only one active default rule per table. E11
    4. Restrict non rota admin (order 1000): such a global rule needs rota_admin. E10

    Migrate Trigger when group assigned shows old rules in the new form. E12 Client scripts on the form clear the trigger fields when the table or run mode changes, and show the field for the chosen action. E48 The choices are Run once or Every time trigger field changes, Condition matches or Default, and Subflow or Script. E13

    3. Trigger rules: running NEW

    1. The events trigger_rule.process (initial assignment) and trigger_rule.reassignment (group change) run script actions that call TriggerRule.process. E16 With com.snc.on_call_rotation.new_trigger_engine true E19, rules with a Subflow action go through On-Call: New Trigger Engine Handler. E18 What queues the events is platform code the mirror doesn't hold.
    2. TriggerRuleSNC.process stops unless the record has the group and user fields, a group, and an assignee outside that group. E17
    3. It cancels earlier on-call subflows and workflows on the record, starts the subflow in the background with the record and field names, and logs it in trigger_rule_wf_context. E17
    4. The subflow comes from the category On-Call Escalation Triggers E14 E15; only subflows are supported (glide.oncall.only_flow_enabled_release true). E20

    4. The default escalation NEW

    Without a custom policy the line-up is built from the rosters: one on-call person per roster in order, or, with a single roster, its members in turn; each roster's reminders, delays and forced channel apply. E21 E22

    Catch-all (catch_all): individual needs catch_all_member E23, all needs catch_all_roster E24, group_manager shows the group's manager E25; hidden on a custom escalation. E26 The wait is the shift's catch_all_wait_time, else the property, which has no value, so 0. E27 E28 Q07

    6. Channels NEW

    ChannelSubflowAccept / reject
    EmailOn-Call: Send Notification EmailACC / REJ E41
    SMSOn-Call: Send Notification SMSmessage number + ACC / REJ E42
    VoiceOn-Call: Send Notification Voice1 / 2 E43

    All three are the active defaults, with no table or condition. E41 E42 E43 SMS and voice go through Notify; no Notify number is set for on-call calls from the browser E45 shared/Q01, and Assign by Acknowledgement uses a Notify conference call rather than a plain call. E44

    • Q07 Should an instance-wide catch-all wait time be set, now that the property has no value? Decision, for the process owner
    • shared/Q01 Notify is off and no telephony provider is switched on, so SMS, voice and conference calls are unavailable (Send Sms on changes, incidents, problems and requests, the on-call flows and task actions, and the text-message code of self-service password reset); should Notify be set up with a provider, and if not, should password reset's text-message check be made optional or replaced? Decision, for the platform owner
